## 2026-08-26 — [ONB-02, IDT-03, MAP-01, MAP-09, SUG-DES-011] issue #128 E2E flakiness: 429 observability + gate back to green

- **Root cause (issue #128):** `/auth/otp/request` and `/auth/otp/verify` share IDT-03's per-IP rate limit (10/60s, `apps/api/src/routes/auth.ts`). Every `signUpThroughOtp()` spends 3 calls on that one bucket, so a full suite (~16 onboarding call sites, ~48 calls) exhausted it part-way through. The 429 left `SignupViewModel` silently in `otpError`, and `waitUntilContentDescriptionExists` then polled 20s before throwing `ComposeTimeoutException` — a timeout that never named its real cause.
- **The fix is server-side, not here:** PR #139 added `OTP_RATE_LIMIT` tiers; `apps/api/tests/dev-local-server.ts` (the entrypoint `scripts/e2e-android.sh` requires) now boots `relaxed` at 100 req / 20 min. ~48 calls fit comfortably. No client-side pacing is needed at all.
- **What this PR actually contributes:** `SignupViewModel.verifyOtp`'s failure branch now emits `logger.event(level, "otp.verify.failed", {status})` — numeric status only, no phone hash or OTP (G3). That branch used to be completely silent, which is why #128 took a live logcat session to diagnose. 401 (an ordinary mistyped code) logs at INFO; everything else, including 429, stays WARN — review caught that logging 401 at WARN would bury the 429s this exists to surface under routine typo volume. `otpError` remains the UI state: no spec copy exists yet for a distinct rate-limited message (G4). Pinned by regression tests in `SignupViewModelTest`.
- **Also:** `MAP-01`/`MAP-09` return to `automated` in `docs/qa/e2e-coverage.json`, and `SUG-DES-011` (`FicheTouchTargetsTest` x3) is added to that manifest plus its scenario in `docs/qa/e2e-scenarios.md` for the first time — the tests existed but were neither drift-guarded nor documented, a pre-existing gap review caught.
- **Gotcha — do not rebuild the deleted `OtpRateGate`.** An earlier revision of this PR paced calls via timestamps written to `/sdcard` with `UiAutomation.executeShellCommand("sh -c '…'")`. There is no shell behind that API: AOSP hands the string to `Runtime.getRuntime().exec(String)`, which tokenises on whitespace and ignores quotes, so it actually exec'd `sh -c "'mkdir"` and silently no-opped (stderr discarded). If pacing is ever genuinely needed, use `executeShellCommandRw("sh")` and write the script to the returned stdin pipe. Three other dead ends are recorded in the deleted file's history: in-memory state (`ANDROIDX_TEST_ORCHESTRATOR` runs each `@Test` in a fresh process), a raw `File` under a cross-UID test-package path, and `PlatformTestStorageRegistry` (asymmetric input/output channels, not a shared store).
- **Verified:** `scripts/e2e-android.sh` on a booted API-34 `Pixel_6_Pro` against a post-#139 local API — **39/39 passed, 0 failed, 0 skipped, zero drift-guard failures** (`test-results/e2e/e2e-report.md`). Prior baseline was 18/46 failing. Test count is 39 rather than 46 because `OtpRateGateTest`'s 7 cases were deleted with the helper; nothing else was dropped. Unit: `SignupViewModelTest` 6/6, full suite 190/190.
- Related: #56 (API 34 emulator pin) remains the other standing constraint on this suite.

## 2026-08-25 — [VLT-10, ONB-08] SUG-AND-001 replay triggers for queued vault writes

- **What changed:** new `sync/SyncScheduler.kt` (+ `PendingSync`) decides *when* queued work leaves the device — post-onboarding, app background (`MainActivity.onStop`), foreground retry, and a debounced write burst — with backoff on repeated identical failures. `Vault` gained an `onPersist` callback, `OnboardingViewModel.complete()` persists `COMPLETE` **before** firing the sync (ONB-08), and `AppContainer` is now created once per **process** on `SwabApplication`.
- **Why:** `syncVault()` had exactly one call site (the Done screen, no retry), so every fiche axis edit stayed on the device forever; and because that call ran *before* `setStep(COMPLETE)`, killing the app within ~20s of « Voir ma carte » resumed on the completion screen instead of the map.
- **Citation corrected (review F1):** this work was specified against VLT-04's *"app background, post-onboarding, after any write burst (debounced ≥30s)"*, which `ab3f241` (ADR-001, 2026-08-16) **deleted**. The current VLT-04 names no trigger and no interval, so the work is re-cited to **VLT-10** ("offline writes queue in a durable local outbox and replay in order on reconnect") plus FS-01 acceptance 1. The triggers and the 30 s window are engineering choices, not spec text. `suggestions/done/android/SUG-AND-001-*.md` was rewritten rather than left as a 100%-similarity rename.
- **One container per process (review F3), the bug this PR nearly shipped:** `viewModel { }` initializers do not re-run after an Activity recreation (SUG-AND-003), so a per-Activity container left the surviving ViewModels writing to a dead `Vault`/`SyncScheduler` while `onStop`/`onStart` drove a fresh one whose queue was always empty. Rotate, edit a fiche, press Home inside the debounce window and the background trigger no-opped. Pinned on-device by `SyncAcrossRecreationE2ETest` (proven red against the old wiring) plus a structural guard that `AppContainer` is constructed exactly once, by `SwabApplication`.
- **Backoff (review F2):** one free retry, then 60 s doubling to a 1 h cap, reset when the failure *type* changes. Issue #127 means the first push of every new account cannot succeed, and with `onStart`+`onStop` wired that was six doomed requests per app switch, forever. Values mirror iOS so both platforms behave alike.
- **Still not met: FS-01 acceptance 1.** #127 blocks it — the base-version handshake is wrong on both platforms and Android additionally decodes `POST /vault`'s `{version}` reply as a type whose `blob` is required, so even a 200 throws. This PR fixes *when* sync fires, not that protocol; `test_VLT10_againstTheRealServerResponseShape_thePushStillFails_issue127` pins it, and the test doubles here now return exactly what the API sends.
- **Gotchas for the next person:** `advanceUntilIdle()` never dispatches `backgroundScope` work, so scheduler assertions built on it pass vacuously — use `runCurrent()`/`advanceTimeBy()`. The debounce timer and the flush are separate jobs on purpose: cancelling the timer must not kill an in-flight push. `getEncryptedVault()`'s first-blob write passes `notify = false`, or a read-only sync re-arms itself.
- **Deferred:** no `ConnectivityManager` callback (foreground approximates reconnect); no durable outbox — the queue is in memory, mitigated by assuming pending work at launch when onboarding is already complete. Both land with ADR-001 stage 4.
- Verified: `./gradlew test` **188/188 per variant** (31 new cases), JaCoCo domain floor green at 90.1% overall / 95.8% for `sync`. E2E: the full gate is **red on `main` too** (pre-existing `ComposeTimeoutException` flakiness, issue #128) — `scripts/e2e-android.sh` aborts under `set -e` before the report generator, so the requirement report was produced by running `scripts/e2e-report.mjs` **by hand**; no PASS is claimed. `SyncAcrossRecreationE2ETest` was run directly and passes.

## 2026-08-21 — [VLT-01, ONB-02] SUG-AND-010 lock getOrCreateVaultKey against concurrent first calls

- **What changed:** `AndroidKeystoreVaultKeyStore.getOrCreateVaultKey()` and `InMemoryVaultKeyStore.getOrCreateVaultKey()` now run their check-then-act body under a `Mutex` (same `kotlinx.coroutines.sync.Mutex` pattern as `Vault.kt`, no new dependency).
- **Why:** the method was check-then-act with no synchronization. `SignupViewModel.verifyOtp` calls it in its own `viewModelScope`, independently of `Vault.hydrate()`/`persist()`'s calls — two concurrent first calls could both see no wrapped key, mint two different 32-byte keys, and whichever lost the `kv.set` race left its own data permanently undecryptable (SUG-AND-004's crash loop).
- **Covered transitively:** `AndroidKeystoreVaultKeyStore` is the only caller that ever touches `WRAP_KEY_ALIAS`, so `KeystoreEnvelope.getOrCreateKey()`'s own check-then-act on that alias is now serialized too — no separate lock needed there.
- **Tests:** new `VaultKeyStoreConcurrencyTest` (JVM, `InMemoryVaultKeyStore`, 50-way concurrent `getOrCreateVaultKey()` on `Dispatchers.Default` for real thread parallelism) — reliably fails pre-fix, deterministically passes post-fix. New instrumented `test_VLT01_concurrentGetOrCreate_singleKeyPersisted` in `AndroidKeystoreVaultKeyStoreTest` (real Keystore, runs in `scripts/e2e-android.sh`).
- `./gradlew test` **157/157 per variant** (count includes the 6 cases SUG-AND-013 added on `main`; this PR adds 1), `jacocoDomainCoverageVerification` and `lintDebug` green. Mutation-checked: removing the `Mutex` from `InMemoryVaultKeyStore` fails the concurrency test on 3/3 runs. E2E gate not run this PR (no emulator available); CI's native matrix covers it.

## 2026-08-21 — [FCH-04] SUG-AND-013 prune vault history to 12 months on write, not just on read

- **What changed:** `Vault.recordAxisEdit` now prunes `history` to the trailing 12 months (new `Vault.HISTORY_RETENTION_MILLIS`) inside its existing lock, in the same persist as the append. `FicheViewModel` drops its own local `TWELVE_MONTHS_MILLIS` and filters against `Vault.HISTORY_RETENTION_MILLIS` instead, so read- and write-time windows can't drift.
- **Why:** the list only ever grew — FCH-04's 12-month window was applied at read time only, so the stored blob kept every axis edit since install. Every chip tap on the fiche is an edit, so an active user with years of re-tags would eventually exceed the 1 MB per-user vault cap and start failing pushes with no client-side handling.
- **Gotcha:** the prune is blob-wide (one flat history list for the whole vault, unlike iOS's per-contact nesting), which is correct — the quota is on the blob and FCH-04 never shows anything out of window regardless of contact. `FicheViewModel`'s read-time filter stays as a second line of defence for blobs written before this landed.
- **Clock-skew guard (do not remove):** the cutoff is corroborated against the newest timestamp already stored before anything is deleted. A naive `cutoff = at - RETENTION` meant a device clock running years fast computed a cutoff in the *future* and deleted every real event for every contact — persisted at once, then pushed by `VaultSync`, which sends the whole blob and re-sends it unmerged on 409, so the loss reaches the server (the VLT-05 restore source). When `at` runs further ahead of the newest stored event than the whole window, a clock jump is indistinguishable from long dormancy, so the write appends without deleting. Growth still stays bounded: blobs grow through *frequent* edits, and frequent edits keep the guard satisfied.
- **Citation correction:** `SUG-AND-013` (and the iOS twin SUG-IOS-007) attribute the 1 MB cap to *VLT-03*. That is pre-ADR-001 wording — FS-07 was rewritten 2026-08-16 and VLT-03 now covers server-side logging/exposure. The cap is real but lives in code, not a current requirement ID: `MAX_VAULT_BYTES` (`apps/api/src/routes/vault.ts:13`) plus a DB `CHECK` (`packages/db` migration `20260818220000`). This entry's code and tests therefore cite **FCH-04**; `apps/android` carries zero `VLT-03` references, matching `main`. `vault.ts:13` still has the stale comment — backend's to fix (G4).
- **Deliberate stopgap, not the end state.** `docs/specs/FS-03-contact-card.md:22` says that post-ADR-001 the 12-month window "becomes a **server-side retention policy rather than a device-side trim**" — which is exactly what this is. Founder's call (2026-08-21): land it anyway, because the ADR-001 server migration is not built and the shipping app still uses the on-device vault, so the cap is a live risk today. **Remove this trim when server-side retention lands** — tracked in #110. The spec text itself is `area:specs` and out of scope for this PR (G4).
- Follow-up noted in code, not implemented: when contact deletion lands, it must also prune that contact's history rows.
- Bookkeeping: `SUG-AND-013` moved to `suggestions/done/android/` with the counts updated. The scope guard explicitly permits this on the area's own PR (`SHARED_ALLOWED_PREFIXES` includes `suggestions/`); skipping it is why those counts had drifted, which the README now records.
- Verified: `./gradlew test` **156/156 per variant** (debug+release), including 6 new cases. Mutation-checked: flipping `>=` to `>` fails the boundary tests, and hard-coding the clock guard to `true` fails both skew regressions. `pnpm turbo run lint typecheck test build` clean except the pre-existing, unrelated `apps/api` `prisma-repo.test.ts` (needs a live Postgres this sandbox doesn't have — CI runs it against its `postgres:17` service).
- **E2E suite is genuinely flaky — budget for re-runs.** `RelationshipMapE2ETest` / `FicheTouchTargetsTest` intermittently fail with `ComposeTimeoutException`. Across **seven** runs of `scripts/e2e-android.sh` (Pixel_6_Pro API 34) the failure count moved 4 → 4 → 0 → 4 → 3 → 1 → 2, always inside those two classes, with *different test names each time* — including one run where `test_SUGDES011_intimiteSegmentedCell` passed while its two siblings in the same class failed. **Clean `main` fails too**, so it is the suite, not this change. An earlier claim here that a warm emulator fixes it was wrong: a fully warm run still failed. `FicheE2ETest.test_FCH04_axisEditAppendsVisibleHistory_newestFirst` — the scenario covering this change — passed in **every** run, as did every other fiche/vault test and `LegacyVaultCompatE2ETest`. **This flakiness blocks the G2 gate for every `area:android` PR and needs its own issue**; it is not fixable from here. Note `e2e-android.sh` runs under `set -e`, so a red suite aborts before the report generator — "zero drift" is only ever claimable from a green run.
- **AVD trap:** a freshly booted emulator is *asleep* with animations at 1.0, and 22/37 fail with `No compose hierarchies found in the app` — nothing to do with the app. Wake + unlock (`adb shell input keyevent KEYCODE_WAKEUP` then `82`) and zero the three `*_animation_scale`/`animator_duration_scale` globals before running the gate.

## 2026-08-20 — [G3] SUG-AND-012 a logging seam + crash reporter, where there was none

- **What changed:** new `observability/SwabLog.kt` (`SwabLogger`: `LogcatLogger` debug-only, `NoopLogger` release/test default), wired through `AppContainer`. `SignupViewModel`'s two anonymous `catch (_: Exception)` blocks, `MainActivity`'s discarded initial-sync failure, and `VaultSync`'s 409-retry path now log an event name + whitelisted scalar fields (never the raw phone number, its hash, tokens, or the vault blob). `ApiClient` sends a fresh `x-request-id` per request — `apps/api` already reads that header (`app.ts:68`), so client and server logs now correlate. New `SwabApplication` installs a default `UncaughtExceptionHandler` (logs exception type only, then rethrows) as the minimum-viable G3 error-boundary reporter.
- **Why:** G3 required structured logging + a single error-boundary reporter; the Android app had zero logger seam (`grep -r "Log\."` found nothing), so a live onboarding/sync failure was undebuggable without adb-less guesswork.
- **Gotcha:** the privacy blacklist is enforced by `SwabLogPrivacyTest`, not just the doc comment on `SwabLogger.event` — never widen a logged field to a free-form string that could carry user data.
- No crash-reporting SaaS added (new dependency, no G4 justification yet) — `SwabApplication` only logs and rethrows.
- E2E gate not run this PR (worker operates without an emulator); JVM suite green (`./gradlew test`).

- **What changed:** new `fiche/ClassificationValues.kt` with `Etat` / `Ressenti` / `RoleContexte` (identifiers per FS-03 § *Stored value vocabulary*). The vault persists `busy`, not `occupé`; `EtatColors.ETAT_COLORS` is keyed by `Etat` instead of by `Fr.ETAT_*`; `FicheFilterConsequence.forValue` takes an `Etat?`; `Vault`'s setters take the typed value, so writing display copy into the vault is a compile error.
- **Why:** ADR-001 stage 0b, mirroring iOS `SUG-IOS-011`. Rewording a label — or shipping the planned Arabic locale — silently orphaned every stored value. After stage 2 these are database columns and the same rewording becomes a data migration.
- **The Kotlin-specific trap this fixes:** Swift's `String ==` compares by canonical equivalence, so « occupé » matches whether stored NFC or NFD. **Kotlin compares UTF-16 code units and does not** — an NFD-encoded legacy token would silently fail to migrate and read as unknown. Both the frozen legacy table and every lookup normalise to NFC. Pinned by a test built from `\u` escapes (a literal would be whatever the editor saved) and verified non-vacuous: removing the NFC pass fails it.
- **Nothing user-visible changes.** Chips render labels, taps carry values. `Vocab` now exposes typed lists plus `*_LABELS`, derived from the enums so the two can no longer drift; `FicheScreen`'s private duplicate `ROLES` list is gone (SUG-AND-017 consolidated ÉTAT/RESSENTI but missed roles).
- **Dual-read is permanent**, applied at the vault's single hydration point. Unknown tokens (`douceur`, `confidente`, still in `vault-test-vectors.json`) round-trip verbatim and render unset. History summaries deliberately keep the display label — FCH-04 hands event creation to the server at stage 2.
- Verified: `./gradlew test` **292/292** · `scripts/e2e-android.sh` **PASS**, 37/37, zero drift (Pixel_6_Pro API 34 — API 35+ still breaks Espresso, issue #56).

## 2026-08-16 — [IDT-02, VLT-01] SUG-AND-006 session tokens are Keystore-encrypted at rest (were plaintext)

- `KeystoreTokenStore` wrote both JWTs as **plaintext** into DataStore despite its name; `Session.kt` claimed "Production storage is Keystore-backed". Neither was true. The refresh token is a long-lived credential, so a rooted device or a bad extraction path yielded account takeover (`allowBackup="false"` helps but is not encryption). ADR-001 raised the stakes: with classification data now server-side, the session token is the only thing guarding a user's whole relationship map.
- New `security/KeystoreEnvelope.kt` holds the envelope crypto, extracted from `AndroidKeystoreVaultKeyStore` so both callers share one proven implementation. Tokens use a **separate alias** `swab.session.wrap.v1` — clearing or invalidating one must not affect the other.
- **Gotcha (do not change):** the vault alias `swab.vault.wrap.v1`, the kv key, and the `IV ‖ CT ‖ TAG` on-disk layout are byte-identical after the extraction — altering any of them bricks every installed vault. `LegacyVaultCompatE2ETest` passing on-device is the proof.
- **Gotcha:** `getOrCreateVaultKey()` still *throws* on failure by design — `Vault.hydrate()`/`persist()` catch it to surface `Unreadable` (SUG-AND-004). Only the token reads fail closed to `null`. Do not "helpfully" make the vault path return null.
- Migration: any value that does not decrypt — including a pre-2026-08-16 plaintext token — reads as `null`, i.e. logged out, and the user re-auths via OTP. Deliberately no JWT-shape sniffing: silently re-encrypting an attacker-planted value is worse than a re-login.
- `SecureTokenStore.getRefreshToken()` added (needed by SUG-AND-007). Tests: 132 JVM green; 14 new/regression instrumented tests green on API 34.
- **E2E gate PASS — 37/37, zero drift** (`scripts/e2e-android.sh`, Pixel_6_Pro API 34). This covers the integrated signup → save-tokens → authenticated-request path, not just the unit round-trip. **Gotcha for the next person:** the gate needs no Docker — boot the API with `buildApp({ repo: fakeRepository(), dbHealth: stub })` and a dummy `DATABASE_URL` (only Prisma reads it) plus `OTP_DEV_CODE=enabled`. It DOES need an **API 34** emulator: on API 37 the pinned Espresso dies in `onIdle` with `NoSuchMethodException: InputManager.getInstance` before any app code runs (issue #56).

## 2026-08-16 — [VLT-01, VLT-05, MAP-05] SUG-AND-004 a corrupt blob or lost Keystore key no longer crashes the app

- `Vault.hydrate()` decrypted+decoded with zero error handling — a tampered/truncated blob, a lost/invalidated Keystore key, or malformed plaintext threw an uncaught exception inside `viewModelScope.launch` (no `CoroutineExceptionHandler`), crashing the process. Since Carte hydrates on launch, one corrupt byte on disk meant a permanent crash loop.
- Added `VaultLoadState` (`Ok`/`Unreadable`) and `Vault.loadState()`. `hydrate()` now catches the decrypt/decode/Keystore failure, sets `Unreadable`, and keeps an empty in-memory `VaultData` — the on-disk blob is left untouched so it stays recoverable. `persist()` rejects writes while `Unreadable` (no-op, not a thrown exception, so unguarded ViewModel callers still can't crash) and also catches a Keystore failure that surfaces only on write.
- `CarteViewModel.vaultUnreadable` surfaces the state; `CarteScreen` shows a calm line (`Fr.CARTE_VAULT_UNREADABLE`, placeholder copy — `⚠️ ASSUMPTION`, mirrors the `FICHE_STALE_TITLE` precedent) instead of hiding the failure behind a quietly-empty map.
- New `VaultCorruptionTest` (truncated blob, wrong-key/tampered blob, no-overwrite-while-unreadable, healthy-blob regression) + one `CarteViewModelTest` case. `./gradlew test`: all suites green.
- Not done: `FicheViewModel`/`ContactsViewModel` still read the vault unguarded — same failure mode on those screens is a follow-up, not required to fix Carte's launch crash.
